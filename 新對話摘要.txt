## 權限白名單修補 + 健診 Groq Key ✅ 2026-07-04 完成

### 背景:共用 Supabase 的跨平台漏洞
- 交易大師與比特聯盟共用同一個 Supabase 專案,auth.users 全專案共用
- 比特聯盟註冊的帳號可直接登入交易大師;其 plan 值(如 master、未來的礦工~至尊)
  不等於 'free',舊判斷「plan !== 'free' 即放行」會讓比特聯盟用戶全站通行
- 另發現 whale.html 與 radar.html 原本完全沒有權限守衛(直接輸入網址可進)

### 修補內容:全站改白名單判斷
- js/supabase.js 末尾新增:
  VALID_PLANS = ['tw','us','all','admin']
  hasAccess(profile) → plan 在白名單內才放行,其他值(含比特聯盟等級)一律視同未開通
- 已改用 hasAccess 的頁面: index(3處)、news、daily、tracker、alerts、
  watchlist(2處)、tutorial、diagnosis
- concepts.html、screener.html(未載入 js/supabase.js):checkAccess 內改為
  ['tw','us','all','admin'].indexOf(plan) !== -1
- whale.html:在 createClient 下方新增權限守衛 IIFE(session檢查+plan白名單,不符跳回首頁)
- radar.html:head 補 supabase-js CDN,fetch helper 上方新增同款守衛
- 新頁面開發規範:一律用白名單判斷,禁止再寫 plan !== 'free'

### 健診改為需要用戶自備 Groq Key(diagnosis.html)
- analyze() 在會員檢查後新增:currentProfile.groq_key 為空 → 擋下並提示
  至「我的帳號」填入(免費申請 console.groq.com)
- AI 呼叫由 callAI(共用 api_keys 輪替池)改為 callGroq(prompt, 2500, currentProfile.groq_key)
  → 健診成本轉嫁到用戶自己的 Groq 免費額度,不再消耗管理員共用 Key,也避免撞 rate limit
- js/supabase.js 的 callAI/api_keys 輪替機制保留未動(其他功能仍可用)
- 用戶填 Key 介面:profile.html 既有(saveAIKeyToDB 存入 profiles.groq_key)

### 待辦(重要)
- 比特聯盟上線前需做鏡像修補:比特聯盟側用自己的等級白名單(礦工~至尊),

## TradingView 指標快訊（直送 Telegram）✅ 2026-07 現行做法

### 架構
```
TradingView 快訊 Webhook → Telegram Bot API 直接發布到頻道
```
- 台股報報（-1003883576984）、美股報報（-1003990900011）
- 不經任何中繼伺服器，TradingView 快訊設定裡直接填 Telegram API 網址

### 限制與注意事項
- TradingView Premium 的篩選器快訊只能對「兩個清單」掃描發布（伺服器端配額，
  中繼站或 Webhook 都無法突破）。目前台股、美股各用掉名額
- 想擴充標的：優先把清單「加大」（單一清單可容納數百檔）而不是「加多」；
  再不夠的選項：升級 Ultimate，或自建掃描器（參考 daily_scanner.py 模式，
  GitHub Actions/Railway 排程 + Telegram 推播，不受配額限制）
- Bot Token 寫在每條 TradingView 快訊的 URL 裡，若 Token 重置需逐條更新
- 台股訊號只顯示代號、無中文名稱補齊（原補名功能隨 tw-alert-bot 除役）

### 歷史紀錄
- 前代方案 tw-alert-bot（TradingView → Railway FastAPI → 查 tw_stocks 補中文名 → Telegram）
  已於 2026-07 除役，Railway 服務已關閉，GitHub repo（BitoCat/tw-alert-bot）保留封存。
  未來若要恢復「補中文名／訊息加工／分流」需求，可參考該 repo 重建

## 技術架構

### 前端（GitHub Pages）
純靜態 HTML + JS，無框架。

**重要限制：**
- Safari 不支援 AbortSignal.timeout()：所有 fetch 不可加此參數
- supabase-js 在 GitHub Pages 環境 apikey header 帶不進去：新頁面用直接 fetch；舊頁面需在 head 加 CDN：
  ```html
  <script src="https://cdn.jsdelivr.net/npm/@supabase/supabase-js@2.39.3/dist/umd/supabase.js"></script>
  <script src="js/supabase.js"></script>
  ```
- 新頁面（radar.html、news.html、daily.html 強力買入區）使用直接 fetch
- GitHub Pages 有 CSP 限制，內嵌 script 可能被擋 → 付款頁面放在 Railway 上

**Supabase 直接 fetch 標準寫法：**
```javascript
const SUPABASE_URL = 'https://kldumnxdlgovaxtiszyn.supabase.co';
const SUPABASE_ANON = 'eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...';
const SB_HEADERS = {
  'apikey': SUPABASE_ANON,
  'Authorization': 'Bearer ' + SUPABASE_ANON,
};
```

## 概念股雷達（concepts.html）✅ 2026-06-11 完成（台股+美股）

### 架構
concepts.html（🇹🇼/🇺🇸 切換頁籤）
→ data/concepts.json（台股 20 概念約 150 檔）
→ data/us_concepts.json（美股 18 概念約 100 檔）
→ Railway POST /concept-analysis（批次估值，concept_analysis.py Blueprint）

### 概念清單維護（不用動程式）
- 直接編輯 JSON：台股 data/concepts.json、美股 data/us_concepts.json
- 台股 code 只放四碼數字（後端自動試 .TW 再 .TWO）；美股直接放代號（NVDA）
- category 可自由新增，前端自動產生新分組按鈕
- 金融類概念加 "valuation_hint": "pb"（台股金融股、美國銀行股已標）
- 單一概念檔數無硬上限：超過15檔時前端自動分批呼叫後端（每批15檔）再合併，
  25檔約20-40秒（快取後秒回）。建議單一概念控制在25檔內以維持聚焦比較
- JSON 改壞時整片按鈕會消失 → 用 jsonlint.com 驗證（常見錯誤：多/少逗號、全形引號）
- 美股特殊代號：Block=XYZ（原SQ）、SanDisk=SNDK（2025從威騰分拆）

### 後端（trading-bot/concept_analysis.py，Flask Blueprint）
- 註冊：主程式 app = Flask 下方 from concept_analysis import concept_bp + register_blueprint

■ 最重要的教訓:T86 是 19 欄,不是 10 欄
--------------------------------------------------------------
taiwan_scanner.py 的 fetch_twse_institutional 原本欄位 index 全錯位,
導致 tw_institutional 的 trust_net(投信)整欄=0、dealer/total 也錯格。
症狀:外資有值、自營有值、合計有值,唯獨投信全 0,且合計≠外資+投信+自營。

證交所 T86 正確端點與欄位(19 欄):
  https://www.twse.com.tw/rwd/zh/fund/T86?date=YYYYMMDD&selectType=ALL&response=json
  row[0]=代號 row[1]=名稱
  row[2/3/4]  = 外資 買/賣/淨
  row[5/6/7]  = 外資自營商 買/賣/淨(通常0)
  row[8/9/10] = 投信 買/賣/淨   ← 投信淨買是 row[10]!
  row[11]     = 自營商 買賣超(合計)
  row[12~17]  = 自營商(自行買賣)、(避險)明細
  row[18]     = 三大法人買賣超(合計)
單位是「股」,除 1000 換「張」。寫入前檢查 raw.get("stat")=="OK"。

■ 籌碼面觀念(毛哥的核心主張,已內化進系統)
--------------------------------------------------------------
- 主角是「投信」:外資常左側交易、題材結束就跑;投信低點接手才是吸籌主力。
  外資/自營只顯示不當門檻(自營多為避險雜訊)。
- 吸籌本質=投信積極持續買 + 控量不抬價。所以「投信連買」是必要條件(非零散)。
- 吸籌 vs 追買 的分野 = 股價有沒有被推高(近5日漲<3%=吸籌,≥3%=追買),兩者都要投信連買。
- 底部 vs 中段(用均線位置「顯示」判斷,不當篩選,以免退回技術面):
  · 底部吸籌 = 季線下(跌深打底,左側抄底,稀有珍貴)
  · 中段吸籌 = 月線季線間/站上均線(波段回檔整理,右側加碼,線圖難察靠籌碼)
- 集中度用「相對比例」不用絕對張數(業界標準:買超÷成交量,≥10%才有意義)。
  小型股買500張佔20%=強;台積電買5000張佔比極小=雜訊。
- 純度:投信正+合計正=三大同買(共識強);投信正+合計負=外資倒投信接(底部吸籌典型)。
